# Project Requirements Document (PRD)
## Stock Price Prediction Web App (LSTM)

**Owner:** You
**Date:** 2026-08-29
**Status:** Draft v1

---

## 1. Overview

A web application that lets a user pick a stock ticker and see a forecast of its future closing price, generated by an LSTM neural network trained on historical price data. This is an educational/portfolio project demonstrating time-series forecasting with deep learning, wrapped in a usable web UI — **not** a real trading or investment tool.

## 2. Goals / Non-Goals

**Goals**
- Let a user search for a stock and view historical price charts.
- Generate an N-day-ahead closing price forecast using an LSTM model.
- Show forecast accuracy metrics (RMSE/MAE) so the user can judge model quality.
- Support any reasonably liquid, publicly traded ticker (not just a fixed list).
- Keep infrastructure and cost minimal (single small server / free-tier friendly).

**Non-Goals**
- Not a trading platform (no buy/sell execution, no brokerage integration).
- Not intraday/high-frequency prediction — daily granularity only for v1.
- Not guaranteeing predictive accuracy — stock prices are noisy and largely unpredictable; this is explicitly communicated in the UI.
- No user accounts / auth in v1 (can be added later).

## 3. Users & Use Cases

- **Primary user:** someone curious about a stock who wants a data-driven, visual forecast alongside historical context.
- **Use case 1:** User types "AAPL" → sees 1-year historical chart → requests a 7-day forecast → sees forecast overlaid on the chart with a confidence caveat.
- **Use case 2:** User picks a ticker that has never been requested before → system trains a model in the background → user sees a "training, check back shortly" state, then the result.

## 4. Functional Requirements

| ID | Requirement |
|----|-------------|
| F1 | User can search/select a stock ticker (autocomplete on symbol or company name). |
| F2 | User can view historical OHLCV price data as a chart (1M/6M/1Y/5Y ranges). |
| F3 | User can request a price forecast for a configurable horizon (e.g., 7/14/30 days). |
| F4 | System fetches historical data from an external market-data source. |
| F5 | System preprocesses data (normalization, sliding-window sequences) for the LSTM. |
| F6 | System trains and/or reuses an LSTM model per ticker. |
| F7 | System returns predicted closing prices for the requested horizon. |
| F8 | UI displays historical + predicted prices on one chart, visually distinguished. |
| F9 | System shows model quality metrics (RMSE, MAE) computed on a held-out validation window. |
| F10 | System caches predictions so repeated requests for the same ticker/horizon don't retrain/refetch unnecessarily. |
| F11 | System handles invalid/unknown tickers and upstream data-source failures gracefully with a clear error message. |
| F12 | A visible disclaimer states this is not financial advice and forecasts carry significant uncertainty. |

## 5. Non-Functional Requirements

| Category | Requirement |
|----------|-------------|
| Latency | Cached predictions return in < 1s. A first-time (cold) ticker request should acknowledge within ~1s and complete training within a few minutes, surfaced via async status. |
| Scalability | MVP: tens of concurrent users. Design should not block a path to horizontal scaling later. |
| Cost | Use free-tier data sources and infrastructure where possible for MVP. |
| Availability | Best-effort for MVP (no formal SLA); degrade gracefully if the data source is down (serve last-cached data with a staleness notice). |
| Data freshness | Historical data refreshed at least daily (market data doesn't need real-time streaming for v1). |
| Maintainability | Clear separation between data fetching, preprocessing, model training/serving, and API/UI layers so any piece (e.g., swapping data source or model type) can change independently. |
| Security | No sensitive user data collected in v1 (no auth), so attack surface is limited to API abuse — needs basic rate limiting. |

## 6. Constraints

- **Stack:** Python + TensorFlow/Keras for modeling (per your preference).
- **Team size:** solo/small — favor simplicity and managed/free services over heavy infrastructure.
- **Data source:** no paid API budget assumed for MVP (see ADR-001 for the recommendation and trade-offs).
- **Timeline:** phased — MVP first (single-ticker demo quality), then generalize.

## 7. Success Metrics

- Model produces a forecast with RMSE meaningfully better than a naive baseline (e.g., "tomorrow = today") on held-out data — this is the real bar, since beating naive persistence is the honest test for short-horizon price forecasting.
- End-to-end request (search → chart → forecast) completable in under a few minutes for a brand-new ticker, under a few seconds for a cached one.
- Zero unhandled crashes on invalid ticker input or upstream API errors during a demo session.

## 8. Open Questions (to revisit as you build)

- Which tickers should be "pre-warmed" (pretrained at deploy time) vs trained on demand? (See ADR-002.)
- Do you want just closing-price prediction, or also volume/volatility indicators as model inputs?
- Should the UI ever show multiple horizons at once, or one at a time?
- How often should models be retrained as new daily data arrives (nightly job? weekly?)

## 9. Risks

| Risk | Mitigation |
|------|-----------|
| Stock prices are close to a random walk; LSTM may not meaningfully outperform naive baselines. | Set expectations in UI copy; always show baseline comparison alongside model metrics so the user can judge for themselves. |
| Unofficial free data sources (e.g., Yahoo Finance via yfinance) can change or rate-limit without notice. | Cache aggressively; isolate the data-fetching layer behind an interface so the source can be swapped (see ADR-001). |
| On-demand training for arbitrary tickers could be abused (denial-of-wallet/compute). | Rate-limit training requests per IP; cap concurrent training jobs; consider a fixed initial ticker universe for v1. |
